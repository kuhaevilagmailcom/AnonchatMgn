# АНОН МГН — безопасное обновление устойчивости (PR #26)

> Этот PR нельзя автоматически считать проверенным продакшен-релизом: требуется
> тестовая копия БД и прогон в отдельном окружении Bothost.

## Что изменено

- Административные баны/муты/ручные изменения ⭐ создают запись уведомления в
  SQLite в одной транзакции с соответствующим изменением.
- Telegram-доставщик обрабатывает `admin_notice_outbox`, сохраняет результаты и
  после рестарта продолжает обработку незавершённых записей.
- История сообщений для Mini App сохраняется в `miniapp_events`.
- Временные муты и баны имеют постоянные таблицы сроков. Janitor снимает
  окончившиеся ограничения и создаёт уведомления.
- Состояние aiogram FSM хранится в `fsm_storage` (вместо MemoryStorage).
- Рассылки теперь имеют постоянные `admin_broadcast_jobs` и
  `admin_broadcast_targets`; прогресс можно открыть повторно из админки.
- Добавлены проверяемые резервные копии SQLite, диагностические индикаторы,
  сокращён интервал записи матчмейкера и добавлена автоматическая повторная
  попытка при ошибках SQLite.

## Перед деплоем

1. Сохранить текущий SQLite файл и файлы `-wal`, `-shm` **через SQLite backup API
   либо после остановки бота**. Простое копирование только `.db` во время работы
   может быть несогласованным.
2. Проверить, что `DATABASE_PATH` указывает на тот же постоянный диск Bothost,
   что и до обновления; каталог `data` не должен пересоздаваться.
3. Скопировать рабочие секреты в защищённые переменные окружения; не заливать
   `.env` и токены в GitHub.
4. По желанию задать `BACKUP_DIR` на отдельный постоянный том и
   `BACKUP_KEEP_COUNT=7`. По умолчанию копии идут в `data/backups`.
5. На копии базы проверить миграции, работу `/admin`, выдачу/снятие наказания
   и ручное начисление/списание очков.
6. Выполнить `python -m tests.admin_reliability`,
   `python -m tests.admin_miniapp`, `python -m tests.core`,
   `python -m tests.flow` и `python -m compileall -q .`.
7. Проверить `/api/miniapp/health` и админку > Диагностика.
8. Проверить остановку и повторный запуск сервера с активной тестовой парой,
   очередью и незавершённой тестовой рассылкой.

## Ограничения и нюансы

- Telegram Bot API не предоставляет гарантированное подтверждение exactly-once
  отправки при обрыве сети после фактической доставки. Для рассылок такие
  получатели получают `uncertain`, **автоматического повтора нет**.
  Для уведомлений повтор потенциально может создать дубликат после
  неоднозначного исхода, но основное изменение/права не дублируются.
- Самые последние изменения матчмейкера всё ещё сохраняются асинхронно:
  интервал теперь 0.3 сек вместо 5 сек, а запись повторяется после ошибки.
  Это **снижает**, но не устраняет полностью окно потери неподтверждённого
  состояния при `SIGKILL`.
- Бэкапы по умолчанию локальные. Для восстановления после потери сервера
  организуйте независимое внешнее копирование каталога бэкапов.
- Параллельное выполнение нескольких копий бота с одним Telegram-токеном
  **не поддерживается**. Для масштабирования нужно отдельно согласовать
  распределённые блокировки, сервис состояния матчмейкера и фоновую доставку.
- Дневные начисления, игровые награды, ограничения и механики не изменялись.
- Для старых мутов/банов без сохранённого срока в новых таблицах автоматическое
  уведомление об истечении не создаётся; старые бессрочные баны остаются в силе.
- Это обновление не создаёт постоянный архив приватных переписок.

## Откат

1. Остановить бота, чтобы избежать конкурирующих polling-процессов.
2. Вернуть предыдущий код.
3. Если новая схема уже применена, существующая БД содержит дополнительные
   таблицы и колонку `users.ban_until` — старый код обычно их игнорирует;
   **не удаляйте эти таблицы**, чтобы не потерять незавершённые уведомления.
4. Если нужен полный откат с восстановлением базы, используйте только проверенную
   резервную копию; учитывайте, что так могут пропасть действия, совершённые
   после её создания.
5. Перед повторным применением изменений протестируйте миграции на копии базы.
